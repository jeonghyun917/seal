### 1-3. P1 — 파기 후 증적이 다시 생성될 수 있는 경합

**조건:** 증적 작업자가 개인정보를 읽어 생성 중인 상태에서 파기가 실행되고, 그 뒤 증적 생성이 완료되는 경우.

파기 SQL은 `FINALIZED` 상태의 증적만 대상으로 한다. `PROCESSING` 작업의 처리 권한과 버전은 무효화되지 않는다. 따라서 작업자가 이미 읽은 개인정보로 PDF를 만들고 나중에 최종 등록할 수 있다. `QUEUED`/`FAILED`도 파기 대상에서 빠져 후속 생성·재시도 경로가 남는다.

- 근거: `src/main/resources/mybatis/mappers/retention/RetentionMapper.xml:20`, `:22`; `src/main/java/kr/or/arte/seal/evidence/application/EvidenceWorker.java:43`; `src/main/java/kr/or/arte/seal/evidence/persistence/MyBatisEvidenceRepository.java:36`, `:58`

## 2. 대량 운영과 속도

### 2-1. P2 — 이메일 부분 검색이 전체 후보를 읽고 복호화함

목록의 이메일 검색은 100건씩 모든 후보를 메모리로 수집하고 이메일을 복호화한 뒤, 마지막에 현재 페이지 분량을 잘라낸다. 페이지가 20건이어도 서버 작업량은 전체 후보 수에 비례한다. 수신자 선택 검색도 이름·이메일 등을 순회 복호화하며, 검색 결과가 없으면 끝까지 읽는다.

- 근거: `src/main/java/kr/or/arte/seal/recipient/application/RecipientQueryService.java:60`, `:83`, `:119`
- 규모 예시: 후보 15만 명이면 이메일 목록 검색 한 번에 약 1,500회의 배치 조회와 최대 15만 이메일 복호화가 필요하다. 이는 코드상 작업량 계산이며 실측 응답 시간은 아니다.
- 개선: 조직·등록 근거 등으로 후보를 먼저 줄이고, 전체 이메일 일치 검색에는 기존 HMAC 인덱스 활용 가능성을 검토. 부분 검색은 암호화 원칙과 정보 노출을 고려한 별도 검색 인덱스/방식을 설계한다. 속도를 위해 원문 이메일을 평문 저장하는 방식은 권하지 않는다.

- 대량 운영 개선: 개별 ID를 브라우저에 모두 담는 대신 검색 조건/대상 그룹을 서버 작업으로 확정하고 분할 처리. 작업별 성공·실패·재시작 내역 제공.

지금은 전체 색상·폰트를 다시 바꾸기보다 **정보 우선순위와 작업 상태를 통일**하는 편이 효과가 크다.

1. 목록의 첫 정보는 사람이 이해하는 이름/제목, 내부 번호는 보조 정보로 통일.
2. 초안·승인·발송·응답·증적·파기의 다음 가능한 행동과 불가능한 이유를 짧게 표시.
3. 검색 결과 없음, 처음 등록 전, 권한 없음, 서버 오류를 서로 다른 안내로 구분.
4. 대량 작업에는 전체/완료/실패/대기 건수와 작업 시각 표시.
5. 현재 적용된 입력 높이·간격·모바일 메뉴·파기 확인창·오류 접근성 개선은 유지한다. 관련 격리 테스트는 통과했다.

화면 판단에는 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)의 상태 안내·폼·접근성 기준을 참고했다. 실서비스 전체 화면의 시각적 검증을 완료했다는 의미는 아니다.

## 4. 잘 구현된 부분

- 일반 권한 검사는 `@PreAuthorize`, 데이터 범위는 SQL로 분리되어 있다. 위 누락 경로를 일관되게 보완할 기반이 있다.
- 개인정보 암호화·마스킹, 링크 HMAC, 증적 무결성 검증을 이미 적용하고 있다.
- 공개 동의 제출은 세션/요청 잠금과 멱등 처리를 사용한다.
- 통계 엑셀은 스트리밍 워크북과 DB 읽기 전용 반복 읽기 트랜잭션을 사용한다. 전체 결과를 한꺼번에 워크북 메모리에 유지하는 구현보다 적절하다.
- 메일의 SMTP 접수와 최종 수신을 구분하고 재시도/실패 상태를 관리한다.
- JSP 사전 컴파일과 로그인 준비 작업, 공통 폼 동작 테스트가 있다.

## 5. 권장 수정 순서와 완료 기준

1. **접근 통제·파기 안전성:** 1-1~1-4. 실제 두 계정/두 트랜잭션의 회귀 테스트로 차단 확인.
2. **응답 만료 정확성:** 1-5. 경계 시각과 만료 배치 지연 테스트 추가.
3. **대량 운영:** 전체 선택 제한 안내부터 수정하고 검색/목록 쿼리 개선. 1천 → 1만 → 15만 합성 데이터로 부하 확인. 실제 발송 없이 테스트 전송기를 사용.
4. **사용성:** 한글 유형, 대상자·동의서명, 검색, 미저장/다운로드 안내를 정리.
5. **운영 준비:** 별도 테스트 DB의 통합 테스트, 운영 설정 점검, 암호화 키를 포함한 백업 복구 검증, 의존성 보안 점검을 배포 전 수행.

테스트가 현재 통과한다는 사실과 위 경계 조건이 안전하다는 판단은 별개다. 특히 권한 변경, 승인 후 상태 변경, 배치 작업과 파기의 동시 실행을 새 회귀 테스트로 보강해야 한다.

## 6. 후속 구현 기록 (2026-09-29)

- 요청·증적·권리요청 목록의 수신자 정보는 권한 범위 내 일괄 조회로 변경했다. 요청의 양식 정보도 일괄 조회하며 행별 상세 조회를 제거했다.
- 권리요청 목록에 마스킹된 대상자와 관련 동의서명을 표시한다. 권한 밖 동의서명은 표시하지 않는다.
- 증적 목록에 동의서명·요청번호 부분 검색, 생성일 범위, 초기화·조건 유지·오류 안내를 추가했다. 한국 시간의 종료일 전체를 포함한다.
- JSP 컴파일 및 Java 452개, JS/브라우저 32개 테스트 통과. PostgreSQL 17 격리 DB에서 일괄 조회·업무 권한·날짜 경계·동의서명 차단을 별도 검증했다. 검증 범위와 제한은 계획서 진행 기록 참조.
- 운영 서버 반영·커밋·푸시는 수행하지 않았다. 기존 파기 안전성 변경의 DB 패치 20260929_016 적용 및 배포 검증이 필요하다. 15만 건 부하·동시성 스트레스·운영 PostgreSQL 16 검증은 완료한 것으로 간주하지 않는다.

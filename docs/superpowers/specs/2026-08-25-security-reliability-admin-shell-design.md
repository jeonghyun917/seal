# 보안·신뢰성·관리자 공통 셸 보완 설계

## 1. 목적

2026-08-25 전체 검수에서 확인한 조직 범위 쓰기 결함, 키 교체 불안정, 파일시스템과 DB의 비원자적 처리, 메일 중복 가능성, 감사·오류 처리 누락과 관리자 메뉴 소실을 수정한다. 전자서명, SMS·알림톡, OTP, 실명 본인확인, 민감정보·고유식별정보, 만 14세 미만 기능은 계속 제외한다.

## 2. 구현 순서와 릴리스 기준

1. 권리요청 쓰기 권한과 참조 무결성
2. 암호화·HMAC 키 버전 수명주기
3. 파기 실행의 파일·DB 단계 처리와 복구
4. 증적 생성 멱등성과 고아 파일 복구
5. SMTP 결과 기록과 재시도 안전성
6. 중앙 감사, 오류 매핑, 입력·출력 안전성
7. 관리자 공통 헤더·사이드바
8. CI, PostgreSQL 16 검증, 상태 화면과 문서 정합성

P0·P1 항목과 회귀 테스트가 모두 통과하기 전에는 운영 준비 완료로 표시하지 않는다.

## 3. 권리요청 조직 범위와 관계 무결성

- 권리요청 등록은 `actorId`를 필수로 받아 `visible_scope` 안의 조직만 허용한다.
- 대상자는 선택 조직 소속이어야 한다.
- 동의요청을 연결했다면 그 요청은 같은 조직·같은 대상자여야 한다.
- `ERASURE`, `RESTRICTION`, `WITHDRAWAL`은 동의요청 연결을 필수로 한다.
- 긴급 파기와 처리제한 보존 보류도 실행자의 조직 범위를 SQL에서 재검사한다.
- 애플리케이션 검증과 별도로 DB 복합 FK/CHECK로 잘못된 관계 저장을 차단한다.
- 범위 밖 UUID는 존재 여부를 노출하지 않고 404로 처리한다.

## 4. 키 버전 수명주기

### 4.1 권리요청 AES

`detail`, `verification_note`, `result_note`마다 별도의 키 ID를 저장한다. 새 필드를 기록해도 기존 필드의 키 ID는 변경하지 않는다. 파기 시 세 암호문과 세 키 ID를 함께 제거한다.

### 4.2 증적 HMAC

증적 패키지에 `hmac_key_id`를 저장한다. 키 파일은 `keyId=Base64` 키링 형식을 기본으로 하되 기존 32바이트 원시 파일은 기본 키 ID `v1`으로 읽어 하위 호환한다. 생성은 활성 키로, 검증은 패키지에 저장된 키 ID로 수행한다.

### 4.3 링크·이메일 검색 HMAC

활성 키와 과거 검증 키를 함께 읽을 수 있는 키링 인터페이스를 사용한다. 링크 조회는 모든 허용 키의 후보 HMAC을 계산하되 신규 발급은 활성 키만 사용한다. 이메일 정확 검색과 중복 검사는 모든 후보 인덱스를 확인한다. 운영 키 전환 절차는 활성 대상자 재색인 후 이전 키를 제거하는 순서로 문서화한다.

## 5. 파기 실행

파기 실행은 하나의 DB 트랜잭션 안에서 파일을 직접 삭제하지 않는다.

1. 짧은 트랜잭션에서 권한·상태·보존보류·멱등키를 확인하고 `EXECUTING` 및 이벤트를 확정한다.
2. 대상 증적 디렉터리를 동일 파일시스템의 격리 위치로 원자 이동하고 작업별 파일 조작 이력을 남긴다.
3. 별도 트랜잭션에서 주 DB 개인정보 파기, 결과 건수, `EXECUTED` 및 이벤트를 확정한다.
4. DB 확정 뒤 격리 파일을 최종 삭제한다.
5. 실패 시 재실행이 동일 멱등키로 이어지며, DB 파기 전이면 격리 파일을 복원할 수 있어야 한다.

이력은 `APPROVED → EXECUTING → EXECUTED → CONFIRMED`를 빠짐없이 남긴다. 정책은 요청자와 승인자, 실행자와 확인자를 각각 분리하는 2인 교차통제로 확정하고 문서 표현도 이에 맞춘다.

## 6. 증적 생성

- 동일 패키지 경로가 이미 있으면 파일 목록과 SHA-256이 모두 일치할 때 성공 결과로 재사용한다.
- 불일치하면 덮어쓰지 않고 명시적인 충돌 오류로 처리한다.
- DB 최종화 업데이트는 정확히 1건이어야 한다.
- 실패한 임시 디렉터리와 DB 미확정 완성 디렉터리를 탐지·정리하는 복구 경로를 제공한다.
- 증적 생성, 재시도, 검증, 다운로드는 중앙 감사에 구분해 기록한다.

## 7. 메일 전달

- 복호화/콘텐츠 오류, SMTP 오류, SMTP 성공 뒤 DB 상태 기록 오류를 서로 다른 경로로 처리한다.
- 모든 재시도는 Outbox UUID에서 파생한 고정 RFC `Message-ID`를 사용한다.
- SMTP 4xx는 일시 오류, 명확한 5xx는 영구 오류로 분류한다.
- 상태 업데이트는 처리 중 상태와 행 버전을 확인하고 정확히 1건만 변경한다.
- 전달 보장은 `at-least-once`이며 `SMTP_ACCEPTED`는 릴레이 접수만 의미한다.
- 자동 접수·재시도·실패와 관리자 수동 재대기를 중앙 감사에 기록한다.

## 8. 오류·입력·출력 안전성

- 권리요청은 Bean Validation Form DTO를 사용한다.
- 자유 입력값은 서버에서 길이와 허용값을 검증한다.
- 관리자 공통 예외 처리기는 검증 오류 400, 범위 밖/미존재 404, 상태 충돌 409, 내부 오류 500을 안전한 화면으로 매핑한다.
- 오류 화면에는 민감정보나 내부 예외 원문을 표시하지 않고 상관관계 ID만 제공한다.
- 일반 문자열은 JSP에서 항상 `c:out`으로 출력한다. 허용 태그 HTML은 기존 OWASP 정제 결과만 예외로 한다.

## 9. 관리자 공통 셸

- 로그인, 비밀번호 변경, 공개 동의, 이메일 미리보기와 독립 미리보기 화면을 제외한 모든 관리자 업무 페이지에 같은 헤더와 사이드바를 표시한다.
- 사이드바는 대시보드, 동의 업무, 기준정보, 시스템 관리 전체 메뉴를 항상 유지한다.
- 현재 URL을 기준으로 활성 메뉴를 표시한다.
- 데스크톱에서는 고정 열, 모바일에서는 페이지 상단의 가로 스크롤 메뉴로 유지한다. 메뉴를 숨기는 동작은 추가하지 않는다.
- 공통 JSP fragment를 사용해 페이지마다 메뉴가 달라지는 문제를 제거한다.

## 10. 품질 게이트

- 변경 행동은 실패 테스트를 먼저 작성한다.
- 단위·MVC·PostgreSQL 통합 테스트를 분리하되 전체 `verify`에서 모두 실행한다.
- PostgreSQL 16 서비스가 있는 GitHub Actions를 추가한다.
- Java 17, Maven Wrapper, eGovFrame 5.0.0, JSP/JSTL, MyBatis 구조는 유지한다.
- 의존성·정적 분석과 포맷 검사를 CI에 추가하되 새 런타임 인프라나 유료 솔루션은 도입하지 않는다.
- `/system/status`는 로컬 프로필에서만 공개하고 운영에서는 인증된 관리자만 접근한다. 표시값은 하드코딩 대신 실제 런타임/DB 메타데이터를 사용한다.

## 11. 완료 조건

- 다른 조직 UUID로 권리요청·보존보류·파기 작업을 생성할 수 없다.
- 키 `v1`로 저장된 필드는 활성 키가 `v2`가 된 뒤에도 복호화·검증된다.
- 파일 이동 또는 DB 파기 단계에서 강제 실패해도 재실행으로 일관된 종료 상태에 도달한다.
- SMTP 성공 뒤 상태 기록 실패 테스트에서 오류가 콘텐츠 오류로 오분류되지 않고 고정 Message-ID가 유지된다.
- 주요 업무 이벤트가 중앙 감사에서 구분된다.
- 대표 관리자 목록·상세·등록 페이지에서 사이드바가 계속 표시된다.
- 전체 자동화 테스트, DB 검증 SQL, 9090 데스크톱·모바일 스모크가 통과한다.

# 개인정보 전자동의·증적 관리시스템 구축 기획서

> **참고:** 이 문서는 과거 검토본이다. SMS·OTP·전자서명을 제외한 전체 1차 구축의 최신 구현 기준은 `docs/superpowers/specs/2026-08-21-consent-system-full-build-design.md`를 따른다.

**문서 버전:** v2.1  
**작성 기준일:** 2026-08-19  
**문서 성격:** 구축 기획 및 요구사항 기준서  
**대상 독자:** 사업 책임자, 개인정보보호 담당자, 업무 담당자, 개발·보안·운영 담당자

> 본 문서는 개인정보 처리업무에서 필요한 동의의 작성·발송·확인·증적·철회·보유·파기 전 과정을 전자적으로 관리하기 위한 구축 기준을 정의한다. 실제 적용 전에는 기관의 업무 특성, 처리 근거, 관련 개별 법령 및 개인정보·법무 검토 결과를 반영하여 확정한다.

## 0. 요약

본 시스템은 단순히 종이 또는 HWP 동의서를 웹으로 옮기는 도구가 아니다. 개인정보 처리업무별로 처리 근거와 보유정책을 먼저 정의하고, 동의가 필요한 경우에만 정확한 버전의 고지 내용을 정보주체에게 제시하며, 누가·언제·어떤 내용에·어떤 인증 방식으로 의사표시했는지 재현 가능한 증적으로 보존하는 관리체계다.

핵심 구축 원칙은 다음과 같다.

- 동의보다 처리업무와 처리 근거를 먼저 관리한다.
- 수집·이용, 제3자 제공, 민감정보, 선택 항목 등을 개별 동의 객체로 분리한다.
- 발행된 템플릿 버전과 완료된 동의 문서는 수정할 수 없게 한다.
- 문서 해시는 변경 탐지 수단으로 사용하고, 불변 저장소와 무결성 검증값이 포함된 증적 매니페스트로 신뢰성을 보강한다.
- 동의 철회, 처리정지, 보유기간 만료, 파기를 하나의 생명주기로 연결한다.
- 버전관리, 감사로그, 권한관리, 보유·파기는 부가기능이 아니라 MVP의 기반 기능으로 구현한다.

## 1. 사업 개요

### 1.1 추진 배경

기존 개인정보 동의 업무는 Word·HWP 파일의 반복 작성, 수기 서명, 이메일 회신, 스캔본 보관 등으로 분산되어 있다. 이 방식은 최신 서식 사용 여부, 필수·선택 항목 분리, 동의 내용의 사후 변경 여부, 보유기간 만료 및 철회 처리 결과를 일관되게 입증하기 어렵다.

또한 대상자 Excel, 발송 목록, 서명 파일, 최종 PDF와 담당자 메모가 별도로 보관되면 개인정보가 불필요하게 복제되고 권한 통제가 약해진다. 따라서 처리업무 정의부터 파기까지 연결되는 단일 관리체계가 필요하다.

### 1.2 구축 목적

1. 반복적인 동의서 작성·발송 업무를 표준화하고 자동화한다.
2. 개인정보 처리 목적, 처리 근거, 항목, 보유기간을 구조화한다.
3. 정보주체가 모바일 환경에서 명확하게 고지 내용을 확인하고 항목별 의사표시를 할 수 있게 한다.
4. 동의 당시 문서와 이벤트를 재현 가능한 증적으로 생성한다.
5. 철회·처리정지·보유기간·파기까지 후속 조치를 추적한다.
6. 감사 및 개인정보 점검 시 필요한 기록을 권한 범위 안에서 신속하게 조회한다.

### 1.3 목표 성과지표

| 구분 | 지표 | 초기 목표 |
|---|---|---|
| 업무효율 | 1건당 동의 요청 작성시간 | 기존 대비 50% 이상 단축 |
| 품질 | 구버전 서식 발송 | 0건 |
| 추적성 | 완료 건의 증적 패키지 생성률 | 100% |
| 보안 | 권한 없는 원문 조회·다운로드 | 0건 |
| 권리보장 | 철회·처리정지 요청 추적률 | 100% |
| 생명주기 | 파기대상 미처리 건 | 정책상 허용 범위 내 0건 |
| 안정성 | 동일 요청 중복 발송·중복 완료 | 0건 |

### 1.4 설계 원칙

- **적법성:** 동의를 만능 처리 근거로 사용하지 않는다.
- **최소처리:** 업무 목적에 필요한 항목만 수집·표시·보관한다.
- **명확성:** 동의 항목, 거부 권리와 불이익을 읽기 쉽게 제시한다.
- **분리성:** 필수·선택, 수집·이용, 제3자 제공, 민감정보 동의를 구분한다.
- **불변성:** 발행된 버전과 완료 증적은 원본 변경을 허용하지 않는다.
- **재현성:** 당시 문서, 변수값, 동의 결과, 인증 이벤트를 다시 검증할 수 있게 한다.
- **권한 최소화:** 역할과 부서·업무 범위에 따라 조회·발송·다운로드 권한을 제한한다.
- **수명주기 관리:** 수집부터 철회·파기까지 정책과 실행 결과를 연결한다.
- **접근성:** 모바일, 키보드, 화면낭독기 등 다양한 사용 환경을 고려한다.

## 2. 시스템 범위 및 용어

### 2.1 시스템 명칭

권장 명칭은 **개인정보 전자동의·증적 관리시스템**이다. 본 시스템은 전자서명이나 범용 계약 체결을 제공하지 않으며, 개인정보 처리 관련 동의와 증적 관리에 초점을 둔다. 일반 계약·서약서 기능은 범위에서 제외한다.

### 2.2 전체 생명주기

```text
처리업무·근거 등록
  → 템플릿 작성·검토·승인·발행
  → 대상자 반입 근거 확인
  → 동의 요청 스냅샷 생성
  → 발송·전달·재발송
  → 링크 접속·필요 수준의 인증
  → 항목별 동의 또는 미동의
  → 최종 확인·제출
  → 최종 PDF·증적 매니페스트 생성
  → 결과 통지·업무 연계
  → 열람·정정·철회·처리정지 요청 처리
  → 보유기간 만료·법적 보존 검토
  → 승인 또는 자동 파기·결과 기록
```

### 2.3 범위

**MVP 포함 범위**

- 처리업무·처리 근거·보유정책 관리
- 동의 항목 구조화 및 템플릿 버전관리
- 대상자 개별 등록 및 Excel 일괄 반입
- SMS·이메일 발송과 보안 링크
- 모바일 동의, 항목별 동의·미동의 선택과 최종 확인·제출
- 최종 PDF와 증적 매니페스트 생성
- 감사로그, 다운로드 로그, 역할·범위 권한
- 철회 등 권리요청 접수·처리
- 파기예정 산정, 승인 및 파기 결과 기록

**MVP 제외 범위**

- HWP 파일을 그대로 웹 편집기로 변환하는 기능
- 계약 체결·대금 결제·공인 전자문서 유통
- PASS·인증서 기반 전자서명 및 민간 전자서명 사업자 연계
- 카카오 알림톡, SSO, LDAP/AD
- 외부 개인정보처리시스템과 양방향 자동 동기화
- 범용 계약서 작성 및 다자간 계약 체결 워크플로

### 2.4 주요 용어

| 용어 | 정의 |
|---|---|
| 처리업무 | 특정 목적과 근거에 따라 개인정보를 처리하는 업무 단위 |
| 처리 근거 | 동의, 법령상 의무, 공공업무, 계약 이행 등 개인정보 처리의 근거 |
| 템플릿 | 동의서의 편집 가능한 논리적 원본 |
| 템플릿 버전 | 검토·승인을 거쳐 발행된 수정 불가 콘텐츠 |
| 요청 스냅샷 | 대상자에게 제시될 문구, 변수값, 항목과 정책을 요청 시점에 고정한 기록 |
| 동의 항목 | 수집·이용, 제3자 제공 등 정보주체가 개별 결정하는 단위 |
| 증적 매니페스트 | 문서·응답·인증·발송 이벤트의 해시와 식별자를 묶은 검증 기록 |
| 법적 보존 보류 | 파기 대상이지만 개별 법령·분쟁·감사 등 근거로 일정 기간 파기를 중지하는 조치 |

## 3. 사용자 및 권한

### 3.1 사용자 유형

| 역할 | 주요 권한 |
|---|---|
| 시스템 관리자 | 시스템 설정, 조직·계정, 인증·발송 연계 설정. 동의 원문 기본 조회는 제한 |
| 개인정보보호 담당자 | 처리업무·근거·보유정책 검토, 템플릿 승인, 철회·파기 감독, 감사 조회 |
| 부서 관리자 | 소속 부서 템플릿·요청 승인, 담당자 권한 및 진행현황 관리 |
| 업무 담당자 | 허용된 업무의 대상자 등록, 요청 생성·발송, 진행상태 조회 |
| 감사·점검자 | 승인된 기간과 범위의 읽기 전용 조회 및 보고서 출력 |
| 정보주체 | 요청 확인, OTP 인증, 항목별 응답, 최종 제출, 영수증 확인, 권리요청 |

### 3.2 권한 원칙

- 한 사용자는 여러 역할을 가질 수 있다.
- 권한은 역할뿐 아니라 조직, 부서, 처리업무, 데이터 범위를 함께 적용한다.
- 템플릿 작성자와 승인자, 파기 요청자와 승인자, 실행자와 확인자를 각각 분리한다.
- 원문 조회, 대량 다운로드, 엑셀 내보내기, 파기 보류는 별도 고위험 권한으로 관리한다.
- 시스템 관리자는 인프라를 운영하더라도 업무상 개인정보 원문에 기본 접근하지 못하게 한다.
- 관리자 MFA와 세션 만료 정책을 적용한다.
- 권한 부여·변경·회수와 비상권한 사용을 감사로그에 남긴다.

## 4. 개인정보 처리업무 및 정책 관리

### 4.1 처리업무 등록

동의서 작성 전에 다음 항목으로 처리업무를 등록한다.

| 필드 | 설명 |
|---|---|
| 업무명·업무코드 | 처리업무 식별 정보 |
| 운영 부서·책임자 | 업무 소유자와 승인 책임자 |
| 처리 목적 | 구체적이고 제한된 목적 |
| 처리 근거 유형 | 동의, 법령, 계약, 공공업무 등 |
| 근거 상세 | 적용 조문·내부 규정·계약 항목 등 |
| 개인정보 항목 | 일반·민감·고유식별정보 구분 |
| 수집 출처 | 본인, 다른 시스템, 제3자, 공개자료 등 |
| 제3자 제공·처리위탁 | 대상, 목적, 항목, 보유 및 계약 정보 |
| 보유정책 | 기간, 기산점, 파기방법, 법적 보존 근거 |
| 인증 등급 | 링크, 채널 소지 확인, 실명 본인확인 등 |
| 아동 처리 여부 | 만 14세 미만과 법정대리인 동의 절차 적용 여부 |

### 4.2 동의 필요성 판단

처리업무 담당자가 동의를 선택하면 개인정보보호 담당자가 다음을 확인한다.

1. 다른 적법한 처리 근거가 있는데 불필요한 필수동의를 요구하는지 확인한다.
2. 목적 달성에 필요한 최소 항목인지 확인한다.
3. 선택 항목 거부가 서비스 제공 거부로 연결되지 않는지 확인한다.
4. 제3자 제공, 민감정보, 고유식별정보, 홍보 목적이 별도 항목으로 분리됐는지 확인한다.
5. 거부 시 불이익을 추상적 표현이 아닌 실제 영향으로 기재했는지 확인한다.

### 4.3 보유정책 모델

보유기간은 단순히 `수집일 + N년`으로 계산하지 않는다.

- 기산 이벤트: 동의일, 프로그램 종료일, 계약 종료일, 목적 달성일 등
- 기간 단위: 일, 월, 년 또는 특정 종료 이벤트
- 파기 유예: 업무 종료 처리 지연을 고려한 정책상 유예기간
- 법적 보존: 근거 법령과 별도 보존기간
- 보존 방식: 일반 업무 데이터와 논리적·물리적으로 분리
- 파기 방식: DB 삭제·익명화·암호키 폐기·파일 안전 삭제 등
- 확인 책임자: 파기 실행 결과를 확인하는 담당자

## 5. 템플릿 및 동의 항목 관리

### 5.1 템플릿 생명주기

```text
DRAFT → REVIEW_REQUESTED → APPROVED → PUBLISHED → RETIRED
```

- `DRAFT`: 작성자가 편집할 수 있다.
- `REVIEW_REQUESTED`: 검토 중이며 일반 담당자는 사용할 수 없다.
- `APPROVED`: 승인됐으나 발행 전 상태다.
- `PUBLISHED`: 신규 요청 생성에 사용할 수 있는 수정 불가 버전이다.
- `RETIRED`: 신규 요청에는 사용할 수 없으나 기존 증적은 유지한다.

발행된 내용을 변경할 때는 기존 버전을 수정하지 않고 새 버전을 생성한다.

### 5.2 템플릿 구성

템플릿은 HTML 기반 편집 콘텐츠와 구조화된 동의 항목으로 구성한다. HWP·Word 원문은 참고자료로 첨부할 수 있으나 웹 동의의 기준 원본은 발행된 HTML·JSON 스냅샷으로 한다.

지원 변수 예시는 다음과 같다.

```text
{{subject.name}}          {{subject.phoneMasked}}
{{subject.company}}       {{subject.department}}
{{activity.name}}         {{request.sentDate}}
{{custom.eventName}}      {{custom.projectName}}
```

변수에는 자료형, 필수 여부, 최대 길이, 마스킹 여부, 허용 문자와 표시 이름을 정의한다. 렌더링할 때 HTML·스크립트 삽입을 방지하도록 컨텍스트별 이스케이프를 적용한다.

### 5.3 동의 항목 구조

| 유형 | 필수 고지 데이터 |
|---|---|
| 수집·이용 | 목적, 항목, 보유기간, 거부 권리, 거부 시 불이익 |
| 제3자 제공 | 제공받는 자, 제공 목적, 제공 항목, 보유기간, 거부 권리와 불이익 |
| 민감정보 | 민감정보 항목, 목적, 보유기간, 별도 동의 여부 |
| 홍보·선택 | 채널, 목적, 항목, 기간, 선택 거부 영향 |
| 기타 | 적용 법령과 업무 정의에 따른 개별 고지 |

### 5.4 발행 전 자동 검증

- 필수 고지 필드 누락 여부
- 목적과 항목의 비어 있는 값 또는 지나치게 포괄적인 표현
- 필수·선택 항목 결합 여부
- 중복 변수, 미정의 변수, 샘플 데이터 렌더링 오류
- 모바일 화면 및 PDF 페이지 넘침
- 인증 등급과 개인정보 위험도의 정책 불일치
- 보유정책 미연결 여부

## 6. 대상자 등록 및 동의 요청

### 6.1 대상자 반입

대상자는 개별 입력, 승인된 내부 시스템 연계 또는 Excel 업로드로 등록한다. 등록 전에 처리업무, 수집 출처, 반입 근거를 선택해야 한다.

Excel 업로드 절차는 다음과 같다.

1. 양식 다운로드 및 작성
2. 파일 업로드와 악성코드 검사
3. 헤더·자료형·전화번호·이메일 검증
4. 중복 대상자와 동일 요청 중복 확인
5. 정상·오류·경고 건수 미리보기
6. 반입자 확인 또는 승인
7. 대상자 저장 후 원본 업로드 파일 자동 파기

오류 보고서에는 개인정보를 최소 표시하고, 전체 전화번호·이메일이 불필요하게 노출되지 않게 한다.

### 6.2 요청 생성

업무 담당자는 다음 순서로 요청을 생성한다.

1. 처리업무와 발행된 템플릿 버전 선택
2. 대상자 선택
3. 변수값과 동의 항목 확인
4. 발송 채널·만료일·인증 수준 지정
5. 수신 화면과 최종 PDF 미리보기
6. 필요 시 부서 관리자 승인
7. 요청 스냅샷 생성 후 발송 예약 또는 즉시 발송

요청 스냅샷에는 템플릿 버전, 렌더링된 고지 문구, 변수값, 항목 정의, 보유정책, 인증 정책을 포함한다. 발송 이후 템플릿이 바뀌어도 이미 생성된 요청은 영향을 받지 않는다.

### 6.3 대량 요청 통제

- 최대 대상자 수와 일일 발송량 제한
- 대량 발송 승인 기준
- 미리보기 표본과 최종 대상자 수 확인
- 중복 실행을 방지하는 멱등성 키
- 예약 취소 마감시각
- 채널별 비용 예상치와 성공·실패 결과
- 캠페인 단위 일시중지·재개·취소

## 7. 발송 및 외부 접근

### 7.1 발송 채널

MVP는 SMS와 이메일을 지원한다. 메시지에는 필요한 최소 정보만 표시하며 민감한 동의 제목이나 상세 개인정보를 직접 노출하지 않는다.

발송 이력은 요청 상태와 분리하여 관리한다.

```text
QUEUED → SENT → DELIVERED
              ↘ FAILED → RETRY_SCHEDULED → SENT
```

반송·통신사 실패·수신거부·잘못된 주소 등을 구분하고 재시도 횟수와 간격을 정책화한다.

### 7.2 보안 링크

- 최소 128비트 이상의 예측 불가능한 랜덤 토큰 사용
- DB에는 원문 토큰이 아닌 해시값 저장
- URL에 대상자 이름, 요청번호 등 직접 식별자 미포함
- 만료, 폐기, 재발급, 이전 토큰 무효화 지원
- 인증 전에는 동의서 상세정보 최소 노출
- 과도한 접근과 OTP 시도에 대한 속도 제한
- HTTP 접근 차단 및 HTTPS 강제
- 외부 리소스 로딩과 Referer를 통한 토큰 유출 방지
- 링크 미리보기 봇의 GET 요청을 열람 또는 동의로 기록하지 않음

### 7.3 인증 등급

| 등급 | 의미 | 권장 사용 |
|---|---|---|
| A0 링크 확인 | 링크 보유 여부만 확인 | 저위험 단순 고지·동의 |
| A1 채널 소지 확인 | SMS·이메일 OTP로 지정 채널 소지 확인 | 일반 개인정보 동의 |
| A2 실명 본인확인 | 휴대폰 본인확인·PASS 등 외부 인증 | 민감도 또는 부인 위험이 높은 업무 |
| 제외 대상 | 전자서명·전문 전자계약 서비스 | 본 시스템에서 처리하지 않고 별도 업무로 분리 |

인증 실패 횟수, 잠금, 재시도, 대체 경로와 고객지원 절차를 정책화한다. A1을 실명 본인확인으로 표현하지 않는다.

## 8. 정보주체 동의 화면

### 8.1 UX 원칙

- 회원가입을 요구하지 않는다.
- 기본값은 미선택이며 미리 체크된 동의를 사용하지 않는다.
- 동의와 미동의를 동일한 시각적 비중으로 제공한다.
- 필수·선택 및 동의 유형을 화면상 명확히 구분한다.
- 선택동의 거부만으로 다음 단계 진행을 막지 않는다.
- 주요 고지는 지나친 축약 없이 본문에서 확인할 수 있게 한다.
- 모바일 360px 수준에서도 가로 스크롤 없이 이용 가능하게 한다.
- 키보드 탐색, 명도 대비, 입력 레이블, 오류 안내 등 접근성을 적용한다.

### 8.2 화면 흐름

```text
기관·요청자 확인
  → 요청 목적 안내
  → 필요 시 인증
  → 동의 항목별 상세 확인
  → 각 항목 동의·미동의 선택
  → 제출 전 요약 및 최종 확인
  → 동의 결과 제출
  → 완료·영수증 및 권리행사 안내
```

### 8.3 전자적 의사표시 방식

- 요청 대상자의 등록 채널로 OTP 인증
- 각 동의 항목에 대해 동의 또는 미동의를 명시적으로 선택
- 제출 전 전체 선택 결과와 철회 방법 확인
- `동의 결과 제출` 버튼으로 최종 의사표시

손글씨 서명, 성명 서명란, 인증서 기반 전자서명은 사용하지 않는다. 증적은 인증 결과, 제시된 고지 내용, 항목별 적극적 선택, 제출 시각, 템플릿 버전, 문서 무결성과 전체 이벤트를 기준으로 구성한다. 전자서명이 법령상 필요한 업무는 본 시스템의 대상 업무로 등록하지 않는다.

### 8.4 제출 검증

- 모든 필수 결정 항목에 응답했는지 확인
- 선택동의는 미응답 허용 여부를 정책으로 정의
- 요청 만료·취소·이미 완료 여부를 서버에서 재검증
- 중복 클릭에도 한 번만 완료되는 멱등 처리
- 서버 수신 시각을 기준으로 완료 기록
- 완료 후 응답을 직접 수정하지 않고 정정·철회 이력으로 처리

## 9. 증적, PDF 및 무결성

### 9.1 증적 패키지

완료 시 다음을 하나의 논리적 패키지로 생성한다.

- 최종 PDF
- 요청 스냅샷 JSON
- 항목별 동의·미동의 응답
- 발송·전달·열람 이벤트
- 인증 방식·결과·기관 응답 식별자
- 최종 확인 문구와 제출 이벤트
- 템플릿 및 정책 버전
- 서버 수신시각과 시간대
- 필요한 범위의 접속 환경 정보
- 각 산출물 해시가 포함된 증적 매니페스트

접속 IP와 User-Agent도 개인정보가 될 수 있으므로 필요성, 보유기간, 마스킹·축약 여부를 별도로 정한다.

### 9.2 해시 및 불변성

문서 해시는 변경 탐지 값이며 단독으로 정보주체·제출 시점·원본성을 증명하지 않는다. 다음 통제를 함께 적용한다.

1. 최종 PDF와 스냅샷의 SHA-256 계산
2. 파일 식별자와 해시를 증적 매니페스트에 기록
3. 매니페스트에 서버 키 기반 HMAC 또는 동등한 무결성 검증 코드 적용
4. 키는 KMS 또는 HSM 등 별도 키 관리체계에서 보호
5. PDF와 매니페스트를 버전 잠금 또는 WORM 정책이 적용된 저장소에 보관
6. 감사로그는 추가 기록 방식과 변경 탐지 구조 적용
7. 정기 무결성 검증 및 실패 알림

PDF 안에는 자기 자신의 전체 해시를 넣지 않는다. PDF에는 문서번호와 매니페스트 ID를 표시하고, PDF 해시는 외부 매니페스트에 기록한다.

### 9.3 최종 PDF 표시 항목

- 기관명과 동의서 제목
- 정보주체 표시정보
- 동의 당시 목적·항목·보유기간·거부권 안내
- 항목별 동의·미동의 결과
- OTP 인증 완료와 최종 제출 확인 표현
- 동의 완료일시와 시간대
- 인증 방식의 유형
- 문서번호, 템플릿 버전, 증적 매니페스트 ID
- 철회·권리행사 안내

## 10. 상태 및 이력 모델

하나의 상태값에 모든 진행을 담지 않고 영역별 상태를 분리한다.

| 영역 | 주요 상태 |
|---|---|
| 요청 | DRAFT, PENDING_APPROVAL, READY, ACTIVE, EXPIRED, CANCELLED, CLOSED |
| 발송 | QUEUED, SENT, DELIVERED, FAILED, BOUNCED, RETRYING |
| 인증 | NOT_REQUIRED, PENDING, VERIFIED, FAILED, LOCKED |
| 응답 | NOT_STARTED, IN_PROGRESS, SUBMITTED, DECLINED_ALL |
| 문서 | NOT_CREATED, GENERATING, FINALIZED, GENERATION_FAILED |
| 권리요청 | RECEIVED, VERIFYING, PROCESSING, COMPLETED, REJECTED_WITH_BASIS |
| 보유·파기 | RETAINED, DUE, ON_HOLD, APPROVED, DESTROYED, FAILED |

완료 여부는 다음 조건으로 계산한다.

```text
요청 유효
AND 필요한 인증 완료
AND 필수 결정 항목 모두 응답
AND 제출 이벤트 저장
AND 최종 PDF·증적 매니페스트 생성 완료
```

상태 변경은 `STATUS_HISTORY`에 이전 상태, 새 상태, 사유, 수행자, 시각과 연계 이벤트를 기록한다.

## 11. 권리요청, 동의 철회 및 파기

### 11.1 권리요청

정보주체는 동의 완료 화면, 영수증 링크 또는 공개된 기관 절차를 통해 열람·정정·삭제·처리정지·동의 철회를 요청할 수 있다. 요청 방법은 개인정보를 수집한 방법보다 부당하게 어렵지 않게 설계한다.

권리요청에는 신청 유형, 대상 처리업무·동의 항목, 신청일, 본인확인, 처리기한, 결정, 근거, 실행결과와 통지일을 기록한다.

### 11.2 동의 철회

철회는 원본 동의 이벤트를 삭제하거나 덮어쓰지 않는다.

```text
AGREED
  → WITHDRAWAL_REQUESTED
  → WITHDRAWN
  → PROCESSING_STOPPED
  → DATA_DESTROYED 또는 LEGAL_RETENTION
```

동의 항목별 부분 철회를 지원한다. 법령상 의무 등 별도 처리 근거가 있는 데이터는 철회와 무관하게 처리될 수 있으므로, 그 근거와 범위를 정보주체에게 통지할 수 있게 한다.

### 11.3 파기

- 매일 파기예정 산정 작업 수행
- 자동파기 또는 담당자 승인 후 파기 정책 지원
- 파기는 요청자·승인자 및 실행자·확인자 교차 분리 필수
- DB, Object Storage, 검색 인덱스, 캐시, 임시파일과 연계 사본 처리
- 백업은 만료·교체 주기에 따라 복원 불가 상태로 전환하며 복원 시 재파기 통제 적용
- 파기 건수, 방법, 실행자, 확인자, 실패 내역과 재처리 결과 기록
- 다른 법령에 따른 보존은 일반 데이터와 분리하고 접근을 제한

### 13.2 주요 설계 규칙

- 모든 업무 데이터에 조직 또는 테넌트 식별자를 둔다.
- 템플릿과 템플릿 버전을 분리하며 발행 버전은 불변이다.
- 요청에는 템플릿 ID뿐 아니라 요청 당시 스냅샷을 저장한다.
- 동의 결과는 요청 전체가 아니라 동의 항목별로 기록한다.
- 수신자와 정보주체가 다를 수 있는 경우 관계를 별도 모델링한다.
- 역할과 데이터 범위는 다대다 관계로 설계한다.
- 토큰·OTP 원문과 비밀번호는 복원 가능한 형태로 저장하지 않는다.
- 최종 PDF는 암호화된 Object Storage에 저장하고 DB에는 메타데이터만 저장한다.
- 감사로그는 행위자, 대상, 행위, 결과, 이유, 추적 ID와 시각을 포함한다.
- 파기 시 참조 무결성 때문에 삭제가 막히지 않도록 익명화·분리보존 정책을 설계한다.

### 14.2 권장 기술 원칙

- 관리자와 외부 동의 화면은 배포 단위를 분리할 수 있게 구성한다.
- 발송, PDF 생성, 파기는 메시지 큐 기반 비동기 작업으로 처리한다.
- 요청·응답 API에 멱등성 키와 트랜잭션 경계를 적용한다.
- PDF 생성 실패가 동의 응답 유실로 이어지지 않게 재처리 큐를 둔다.
- Object Storage는 암호화, 버전 잠금, 짧은 유효시간의 제한 접근 URL을 사용한다.
- 키와 비밀정보를 소스·환경파일에 평문 저장하지 않는다.
- 외부 발송·인증 사업자의 장애와 응답 지연을 격리한다.
- 개인정보 검색용 별도 인덱스를 사용할 경우 동일한 접근통제와 파기 연계를 적용한다.

## 18. 핵심 인수 기준

1. 발행된 템플릿 버전은 수정할 수 없고 새 버전으로만 변경된다.
2. 발송된 요청은 요청 당시 고지 내용과 변수값을 동일하게 재현한다.
3. 필수·선택 및 동의 유형이 개별 항목으로 저장된다.
4. 미리 선택된 동의가 없으며 선택동의 거부 후에도 허용된 업무 흐름이 진행된다.
5. 만료·취소된 요청과 중복 제출은 서버에서 차단된다.
6. 완료 건마다 PDF, 응답 스냅샷, 증적 매니페스트가 생성된다.
7. 저장된 문서 또는 매니페스트 변경 시 무결성 검증이 실패한다.
8. 관리자 조회·다운로드·내보내기는 권한 검증과 감사로그를 거친다.
9. 철회는 항목별로 접수되며 처리정지·파기 또는 별도 보존 결과가 연결된다.
10. 보유기간 만료 건은 파기예정 목록에 자동 생성되고 처리 결과가 추적된다.
11. 조직·부서 범위를 벗어난 검색과 직접 객체 접근은 차단된다.
12. 발송·PDF·파기 실패 작업은 원인과 재처리 결과를 확인할 수 있다.

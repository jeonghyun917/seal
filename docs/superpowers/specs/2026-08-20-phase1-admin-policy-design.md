# 1단계 관리자 인증·정책 관리 설계

**상위 기준:** `docs/superpowers/specs/2026-08-21-consent-system-full-build-design.md`
**개발 단계:** 1단계 보안·정책 기반  
**상태:** 구현 설계

## 1. 목표

첫 개발 단위는 모든 후속 관리자 기능이 공통으로 사용하는 DB 기반 인증·권한·감사 기반과 처리업무·보유정책 승인 흐름을 만든다.

완료 시 관리자는 DB 계정으로 로그인하고, 허용된 조직과 권한 범위 안에서 보유정책 및 처리업무 버전을 작성·검토·승인할 수 있다. 승인된 버전은 수정할 수 없고 모든 중요 작업은 감사 이벤트에 기록된다.

## 2. 포함 범위

- 로컬 Git 기준선과 개발 규칙
- `seal_owner`, `seal_app` DB 역할 및 전체 초기 스키마 재정비
- 조직·부서
- 관리자 계정과 DB 기반 로그인
- 임시 비밀번호 변경, 실패 잠금, 수동 잠금 해제
- 역할·권한·조직·처리업무 범위
- 보유정책 논리 객체와 승인 버전
- 처리업무 논리 객체와 승인 버전
- 일반 개인정보 항목
- 작성·검토요청·반려·승인·새 버전·비활성화
- 감사 이벤트와 관리자 감사 조회
- JSP 관리자 화면과 서버 측 입력 검증

## 3. 제외 범위

- 대상자, 요청, 메일, 공개 링크와 동의 제출
- 템플릿 편집과 발행
- PDF와 증적 파일
- Excel 업로드와 ClamAV
- 철회, 권리요청과 파기 작업
- MFA, OTP, SSO와 외부 로그인
- 운영 SMTP와 HTTPS

## 4. 화면과 URL

| 화면 | GET | 변경 요청 |
|---|---|---|
| 로그인 | `/login` | `POST /login` |
| 최초 비밀번호 변경 | `/account/password/change` | `POST /account/password/change` |
| 관리자 홈 | `/admin` | 없음 |
| 조직 목록·상세 | `/admin/organizations`, `/admin/organizations/{id}` | `POST /admin/organizations`, `POST /admin/organizations/{id}` |
| 사용자 목록·상세 | `/admin/users`, `/admin/users/{id}` | 생성, 수정, 잠금해제, 비밀번호 초기화 POST |
| 역할 목록·상세 | `/admin/roles`, `/admin/roles/{id}` | 권한 변경 POST |
| 보유정책 목록·상세 | `/admin/retention-policies`, `/admin/retention-policies/{id}` | 작성·검토·승인·반려·새 버전 POST |
| 처리업무 목록·상세 | `/admin/processing-activities`, `/admin/processing-activities/{id}` | 작성·검토·승인·반려·새 버전 POST |
| 감사 조회 | `/admin/audit-events` | 없음 |

모든 변경은 POST-Redirect-GET 패턴을 사용한다. 삭제 버튼 대신 비활성화를 사용한다. 브라우저에서 JSON API를 직접 호출하지 않는다.

## 5. 관리자 인증

### 5.1 계정

`admin_user`는 다음 정보를 가진다.

- UUID 사용자 ID
- 영문 소문자·숫자·점·하이픈으로 구성된 4~50자 로그인 ID
- 1~100자 표시 이름
- 소속 조직 ID
- BCrypt 비밀번호 해시
- `ACTIVE`, `LOCKED`, `INACTIVE` 상태
- 로그인 실패 횟수와 잠금 해제 시각
- 임시 비밀번호 변경 필요 여부
- 마지막 로그인 시각
- 생성·수정 행위자와 시각
- 낙관적 잠금 버전

로그인 ID는 대소문자를 구분하지 않고 유일하다. 화면 목록에는 비밀번호 해시와 보안 필드를 노출하지 않는다.

### 5.2 비밀번호

- 길이 12~128자
- 로그인 ID와 같은 값 금지
- 앞뒤 공백을 자동 제거하지 않고 입력값 그대로 검증
- BCrypt strength 12
- 관리자 생성·초기화 비밀번호는 임시 비밀번호로 저장
- 임시 비밀번호로 로그인하면 비밀번호 변경 화면 외 관리자 URL 접근 금지
- 변경 성공 시 기존 세션을 무효화하고 새 비밀번호로 다시 로그인
- 비밀번호 원문과 해시는 로그·감사 메타데이터에 저장하지 않음

### 5.3 최초 관리자

사용자 테이블이 비어 있고 다음 환경변수가 모두 제공될 때 한 번만 생성한다.

- `SEAL_BOOTSTRAP_ADMIN_ID`
- `SEAL_BOOTSTRAP_ADMIN_NAME`
- `SEAL_BOOTSTRAP_ADMIN_PASSWORD`

부트스트랩 관리자는 루트 조직과 `SYSTEM_ADMIN` 역할을 가지며 비밀번호를 반드시 변경해야 한다. 사용자 테이블에 한 명이라도 있으면 환경변수가 남아 있어도 추가 계정을 만들지 않는다.

### 5.4 실패 잠금

- 비밀번호 실패를 계정별로 누적한다.
- 5회 연속 실패 시 15분 동안 로그인할 수 없다.
- 잠금 상태의 로그인 시도는 비밀번호 일치 여부를 표시하지 않는다.
- 성공 로그인은 실패 횟수와 임시 잠금 시각을 초기화한다.
- `SYSTEM_ADMIN`은 사용자 상세에서 잠금을 해제할 수 있다.
- 실패·잠금·해제·성공을 감사 이벤트로 기록한다.

## 6. 역할·권한·범위

### 6.1 기본 역할

- `SYSTEM_ADMIN`
- `PRIVACY_OFFICER`
- `DEPARTMENT_MANAGER`
- `OPERATOR`
- `AUDITOR`

### 6.2 권한 코드

- `ORGANIZATION_VIEW`, `ORGANIZATION_MANAGE`
- `USER_VIEW`, `USER_MANAGE`, `USER_UNLOCK`, `USER_RESET_PASSWORD`
- `ROLE_VIEW`, `ROLE_MANAGE`
- `RETENTION_POLICY_VIEW`, `RETENTION_POLICY_EDIT`, `RETENTION_POLICY_REVIEW`, `RETENTION_POLICY_APPROVE`
- `PROCESSING_ACTIVITY_VIEW`, `PROCESSING_ACTIVITY_EDIT`, `PROCESSING_ACTIVITY_REVIEW`, `PROCESSING_ACTIVITY_APPROVE`
- `AUDIT_VIEW`

기본 역할과 권한 코드는 초기 데이터로 넣는다. 역할의 권한 구성은 `SYSTEM_ADMIN`만 변경할 수 있지만 `SYSTEM_ADMIN` 역할 자체에서 `USER_MANAGE`, `ROLE_MANAGE`, `AUDIT_VIEW` 권한을 제거할 수 없다.

### 6.3 데이터 범위

`user_scope`는 사용자에게 허용된 조직 또는 처리업무를 나타낸다.

- `ORGANIZATION` 범위는 지정 조직과 하위 조직에 적용한다.
- `PROCESSING_ACTIVITY` 범위는 특정 처리업무에만 적용한다.
- 루트 조직 범위는 전 기관 범위다.
- 권한 코드가 있어도 데이터 범위에 없는 객체는 조회·변경할 수 없다.
- 존재하지만 범위 밖인 객체는 404로 응답해 객체 존재 여부를 노출하지 않는다.

## 7. 조직

`organization_unit`은 UUID, 조직코드, 조직명, 상위 조직, 활성 여부와 낙관적 잠금 버전을 가진다.

- 조직코드는 영문 대문자·숫자·하이픈 2~30자로 유일하다.
- 루트 조직은 한 개만 존재하며 삭제·비활성화할 수 없다.
- 자기 자신이나 하위 조직을 상위 조직으로 지정할 수 없다.
- 활성 사용자나 활성 처리업무가 속한 조직은 비활성화할 수 없다.
- 비활성 조직에는 새 사용자와 처리업무를 만들 수 없다.

## 8. 보유정책

### 8.1 논리 객체

`retention_policy`는 UUID, 정책코드, 정책명, 소유 조직, `ACTIVE` 또는 `INACTIVE` 상태, 현재 승인 버전 ID를 가진다.

정책코드는 영문 대문자·숫자·하이픈 2~30자로 기관 전체에서 유일하다.

### 8.2 버전

`retention_policy_version`은 다음을 가진다.

- 정책 ID와 1부터 증가하는 버전 번호
- `DRAFT`, `REVIEW_REQUESTED`, `APPROVED`, `SUPERSEDED` 상태
- 기산 이벤트
- 기간 값과 단위
- 파기 유예 일수
- 파기 방식
- 작성자, 검토요청자, 승인자와 시각
- 반려 의견과 낙관적 잠금 버전

기산 이벤트는 `CONSENT_SUBMITTED_AT`, `REQUEST_COMPLETED_AT`, `PROGRAM_END_AT`, `PURPOSE_ACHIEVED_AT` 중 하나다. 기간 값은 1~100, 단위는 `DAY`, `MONTH`, `YEAR`, 유예기간은 0~365일이다. 파기 방식은 `DELETE`, `ANONYMIZE`, `FILE_SECURE_DELETE` 중 하나다.

승인자와 작성자는 달라야 한다. 검토요청 상태에서는 편집할 수 없다. 반려하면 반려 의견을 기록하고 같은 버전을 `DRAFT`로 되돌린다. 새 버전이 승인되면 이전 승인 버전은 `SUPERSEDED`가 된다.

## 9. 처리업무

### 9.1 논리 객체

`processing_activity`는 UUID, 업무코드, 업무명, 소유 조직, `ACTIVE` 또는 `INACTIVE` 상태, 현재 승인 버전 ID를 가진다.

업무코드는 영문 대문자·숫자·하이픈 2~30자로 기관 전체에서 유일하다.

### 9.2 버전

`processing_activity_version`은 다음을 가진다.

- 처리업무 ID와 버전 번호
- `DRAFT`, `REVIEW_REQUESTED`, `APPROVED`, `SUPERSEDED` 상태
- 구체적인 처리 목적
- 근거 유형과 근거 상세
- 승인된 보유정책 버전 ID
- 작성자, 검토요청자, 승인자와 시각
- 반려 의견과 낙관적 잠금 버전

근거 유형은 `CONSENT`, `LAW`, `PUBLIC_TASK`, `CONTRACT`, `OTHER`다. 동의 템플릿과 동의 요청을 만들 수 있는 유형은 `CONSENT`뿐이다. 다른 유형은 동의가 아닌 처리 근거를 명시하기 위해 등록하되 동의 요청 기능에서 선택할 수 없다.

`processing_data_item`은 처리업무 버전에 속하며 항목명, 필요성 설명과 필수 여부를 가진다. 1단계에서는 분류를 `GENERAL`로 고정하고 민감정보·고유식별정보 입력을 제공하지 않는다.

처리 목적은 10~1000자, 근거 상세는 5~1000자다. 처리업무에는 일반 개인정보 항목 한 개 이상과 승인된 보유정책 버전이 필요하다.

승인·반려·새 버전 규칙은 보유정책과 동일하다. 승인된 버전과 이미 사용 중인 논리 객체는 직접 삭제할 수 없다.

## 10. 감사 이벤트

`audit_event`는 추가만 가능한 테이블이다. 다음 필드를 저장한다.

- 서버 발생시각과 DB 수신시각
- 행위자 유형과 사용자 ID
- 작업 코드
- 대상 유형과 대상 ID
- `SUCCESS`, `FAILURE`, `DENIED` 결과
- 사유 코드
- 추적 ID
- 개인정보를 제거한 JSON 메타데이터

1단계 작업 코드는 로그인, 로그아웃, 잠금, 잠금해제, 비밀번호 변경·초기화, 사용자·역할·범위 변경, 조직 변경, 정책·처리업무 작성·검토요청·반려·승인·비활성화다.

감사 조회는 기본 최근 7일, 최대 31일 범위로 제한한다. 행위자, 작업, 결과와 대상 유형으로 검색하며 CSV 내보내기는 1단계에서 제공하지 않는다.

## 11. 입력 검증과 오류

- DTO와 도메인 규칙을 모두 검증한다.
- 클라이언트 검증은 편의 기능이며 서버 검증을 대신하지 않는다.
- 사용자 입력 오류는 같은 화면에서 필드별 한국어 메시지로 표시한다.
- 권한 부족은 403, 범위 밖 또는 없는 객체는 404, 낙관적 잠금 충돌은 409로 처리한다.
- 409 화면은 다른 사용자가 변경했음을 알리고 최신 내용을 다시 불러오는 링크를 제공한다.
- DB 제약 위반과 내부 예외 전문을 화면에 표시하지 않는다.
- 모든 오류 응답에 추적 ID를 표시한다.

## 12. JSP와 접근성

- 관리자 공통 레이아웃은 헤더, 좌측 메뉴, 본문, 사용자 메뉴로 구성한다.
- 현재 사용자 권한이 없는 메뉴는 숨기되 서버 권한검사를 항상 수행한다.
- 모든 입력에는 연결된 `label`, 필수 표시와 오류 설명을 제공한다.
- 키보드만으로 메뉴, 폼, 검토·승인 대화상자를 사용할 수 있어야 한다.
- 상태는 색상만으로 구분하지 않고 텍스트 배지를 함께 사용한다.
- 파괴적인 삭제 대신 비활성화와 명시적인 확인 문구를 사용한다.
- JavaScript는 네이티브 모듈로 작성하고 기능이 없어도 기본 제출 흐름이 동작하게 한다.

## 13. DB 변경 기준

초기 SQL은 로컬 `seal_dev` DB에 적용되었다. 적용된 초기 SQL을 수정하지 않고 이후 변경은 `database/03_patch` 순번 파일로 누적한다.

- DB 생성 스크립트는 `seal_owner` NOLOGIN 역할과 `seal_app` LOGIN 역할을 생성한다.
- 스키마와 테이블은 `seal_owner`가 소유한다.
- `seal_app`에는 필요한 테이블 SELECT·INSERT·UPDATE와 시퀀스 사용 권한만 부여한다.
- `audit_event`에는 SELECT·INSERT만 부여한다.
- 스키마 변경 권한과 테이블 DELETE는 부여하지 않는다.
- 모든 FK, 유일성, 상태, 길이, 범위 제약을 DB에도 둔다.
- `db_change_history`에는 파일 경로, SHA-256, 애플리케이션 버전, 적용자와 적용시각을 저장한다.

## 14. 테스트 전략

### 14.1 단위 테스트

- 비밀번호 정책과 잠금 계산
- 계정 상태와 최초 비밀번호 변경 제한
- 역할·권한·조직 범위 판정
- 조직 순환 참조와 비활성화 제한
- 보유정책 값 검증과 상태 전이
- 처리업무 필수 데이터와 상태 전이
- 작성자와 승인자 분리
- 승인 버전 불변성과 새 버전 교체

### 14.2 MVC·보안 테스트

- 로그인 성공·실패·잠금
- 임시 비밀번호 사용자의 URL 제한
- CSRF 없는 변경 요청 거부
- 권한별 메뉴·URL 허용과 거부
- 범위 밖 객체 404
- 검증 오류와 409 충돌 화면

### 14.3 PostgreSQL 통합 테스트

- 초기 SQL을 빈 `seal_test` DB에 적용
- MyBatis CRUD와 JSONB·UUID·TIMESTAMPTZ 매핑
- 유일성, FK, CHECK와 감사 이벤트 UPDATE·DELETE 금지
- 동시 승인 시 한 요청만 성공
- 적용 SQL SHA-256 이력 확인

H2는 사용하지 않는다. `seal_test`가 준비되기 전에는 단위·MVC 테스트를 실행하고, DB 통합 테스트는 준비 즉시 필수 검증으로 전환한다.

## 15. 완료 조건

1. Spring 인메모리 계정 없이 DB 계정으로 로그인한다.
2. 최초 관리자는 한 번만 생성되고 비밀번호를 변경하기 전에는 다른 관리자 기능을 사용할 수 없다.
3. 5회 연속 로그인 실패 시 15분 잠기며 잠금해제 이력이 남는다.
4. 역할 권한과 조직·처리업무 범위가 서버에서 적용된다.
5. 보유정책과 처리업무는 작성자와 다른 승인자가 승인한다.
6. 승인 버전은 수정할 수 없고 새 승인 버전이 기존 버전을 대체한다.
7. 동의가 아닌 근거 유형은 향후 동의 요청에 사용할 수 없다.
8. 민감정보·고유식별정보·아동 업무 입력 경로가 없다.
9. 주요 성공·실패·거부 이벤트가 개인정보 없이 감사 테이블에 남는다.
10. DB 연결 전 코드 준비 상태는 단위·MVC 테스트와 WAR 패키징 성공으로 판정한다.
11. 1단계 운영 가능 판정 전에는 전용 `seal_test` PostgreSQL에서 모든 통합 테스트가 반드시 성공해야 한다.

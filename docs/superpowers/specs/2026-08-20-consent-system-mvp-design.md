# 개인정보 전자동의·증적 관리시스템 MVP 설계 기준서

**문서 버전:** v2.2  
**확정일:** 2026-08-20  
**상태:** 구현 기준  
**선행 문서:** `docs/개인정보_전자동의_관리시스템_기획서_v2.1.md`  
**우선순위:** 본 문서와 선행 문서가 충돌하면 본 문서를 따른다.

## 1. 목적

본 시스템은 개인정보 처리업무별 동의 내용을 구조화하고, 정보주체에게 이메일로 안내한 뒤 기관 웹페이지에서 항목별 동의·미동의 결과를 제출받아 증적과 후속 조치를 관리한다.

이 시스템은 전자서명, 전자계약 또는 실명 본인확인 시스템이 아니다. 이메일 링크를 받은 사람이 지정 이메일 계정에 접근할 수 있다는 사실만 확인하며, 그 사람의 법적 신원까지 보증하지 않는다.

## 2. 확정 범위

### 2.1 MVP 대상

- 단일 기관 운영
- 만 14세 이상 정보주체
- 일반 개인정보 처리업무
- 이메일 HTML 안내
- 기관 웹페이지의 일회용 보안 링크
- 항목별 동의·미동의와 최종 제출
- 관리자, 역할, 부서 및 처리업무 범위 권한
- 처리업무, 처리 근거 및 보유정책
- 동의서 템플릿 검토·승인·발행 버전
- 대상자 개별 등록과 요청 스냅샷
- PostgreSQL Outbox 기반 메일 발송
- 감사 이벤트, 증적 패키지, 철회 및 파기 관리

### 2.2 제외 대상

- SMS, SMS OTP, 이메일 OTP 및 모든 OTP 입력 절차
- 손글씨 서명, 성명 서명란, 인증서 서명 및 민간 전자서명
- 휴대전화 본인확인, PASS 및 실명 본인확인
- 만 14세 미만 아동과 법정대리인 동의
- 민감정보, 고유식별정보 또는 강한 본인확인이 필요한 업무
- 계약서, 서약서, 결제 및 범용 전자계약
- 메일 열람 추적 픽셀
- 최종 수신 또는 열람 여부 보장
- SMS, 알림톡, SSO, LDAP 및 외부 인증 사업자 연계
- Kafka, Redis, 별도 메시지 브로커, 클라우드 Object Storage 및 유료 KMS
- Flyway와 Liquibase
- jQuery 기본 의존성

제외 대상 업무는 기존 기관 로그인 시스템에서 처리하거나 별도 사업으로 분리한다.

## 3. 핵심 업무 원칙

1. 동의서를 만들기 전에 처리업무, 처리 목적, 처리 근거와 보유정책을 등록한다.
2. 동의가 아닌 다른 적법 근거로 처리하는 항목과 동의가 필요한 항목을 구분한다.
3. 수집·이용, 제3자 제공, 홍보·선택 등 결정 단위를 분리한다.
4. 선택 항목은 미리 선택하지 않고 거부해도 허용된 업무 흐름을 막지 않는다.
5. 발행된 템플릿 버전과 발송된 요청 스냅샷은 수정하지 않는다.
6. 이메일과 웹 동의서는 같은 요청 스냅샷을 원본으로 사용한다.
7. 메일, 링크, 응답, 문서 상태를 서로 분리한다.
8. 완료된 응답은 직접 수정하지 않고 철회·정정·권리요청 이력으로 처리한다.
9. 개인정보 원문 조회, 다운로드, 내보내기와 파기는 권한검사와 감사기록을 거친다.
10. 토큰 원문, 비밀번호, 세션 식별자와 불필요한 개인정보를 로그에 남기지 않는다.

## 4. 사용자와 권한

| 역할 | 주요 책임 |
|---|---|
| `SYSTEM_ADMIN` | 조직·사용자·역할·시스템 설정. 동의 원문 기본 조회 권한 없음 |
| `PRIVACY_OFFICER` | 처리업무·근거·보유정책 검토, 템플릿 승인, 권리요청·파기 감독 |
| `DEPARTMENT_MANAGER` | 소속 부서 요청과 템플릿 검토·승인 |
| `OPERATOR` | 허용된 업무의 대상자 등록, 요청 생성·발송, 진행상태 조회 |
| `AUDITOR` | 승인된 기간·조직·업무 범위의 읽기 전용 감사 조회 |
| 정보주체 | 보안 링크 확인, 항목별 결정, 최종 제출과 완료 결과 확인 |

권한은 역할만으로 결정하지 않는다. `역할 + 조직/부서 + 처리업무 + 작업 권한`을 함께 평가한다. 모든 서버 요청은 URL 접근권한과 대상 객체의 데이터 범위를 다시 검사한다.

### 4.1 관리자 인증

- 운영 코드에서 Spring 기본 인메모리 계정을 제거한다.
- 관리자 계정과 BCrypt 비밀번호 해시는 PostgreSQL에 저장한다.
- 최초 관리자는 사용자 테이블이 비어 있고 부트스트랩 환경변수가 제공된 경우 한 번만 생성한다.
- 초기 생성 후 부트스트랩 비밀번호 환경변수를 제거한다.
- 로그인 성공 시 세션 ID를 재발급하고, 유휴 세션은 30분 후 종료한다.
- 연속 로그인 실패는 계정과 IP 기준으로 제한하고 감사 이벤트를 기록한다.
- 관리자 MFA는 이번 MVP에서 제외한다. 운영 시 관리자 접근망 제한, 강한 비밀번호, 실패 잠금과 정기 권한 검토로 보완한다.

## 5. 기술 및 배포 구조

### 5.1 애플리케이션

- Java 17
- eGovFrame Runtime Maven artifacts 5.0.0
- Spring Boot 3.5.6 / Spring Framework 6.2.11
- Spring MVC / JSP / JSTL
- Spring Security
- MyBatis 3.5 계열
- PostgreSQL JDBC
- Maven Wrapper / 실행형 WAR
- 네이티브 JavaScript, HTML, CSS

### 5.2 단일 서버 운영 구조

```text
외부 사용자
    │ HTTPS 443
    ▼
Nginx
    │ localhost:9090
    ▼
Tomcat 10.1 / seal.war
    ├─ 관리자 JSP
    ├─ 정보주체 모바일 JSP
    ├─ Outbox 스케줄러
    ├─ 증적 생성 작업
    └─ 파기 작업
           │ localhost:5432
           ▼
    PostgreSQL 16.14

증적 파일: /var/lib/seal/documents
애플리케이션 로그: /var/log/seal
최종 백업: 서버 외부 승인 저장소
```

로컬 개발은 `http://localhost:9090`을 사용한다. 로컬 프로필에서는 SMTP 발송을 비활성화하고 보안 쿠키의 `secure` 속성을 끈다. HTTPS, 운영 도메인과 SMTP 실발송은 운영 준비 단계에서만 적용한다.

## 6. 모듈 경계

| 모듈 | 책임 |
|---|---|
| `common` | 보안, 오류, 추적 ID, 공통 검증, 시간·식별자 |
| `admin` | 관리자, 조직, 역할, 권한, 데이터 범위 |
| `policy` | 처리업무, 처리 근거, 개인정보 항목, 보유정책 |
| `template` | 템플릿, 구조화된 동의 항목, 검토·승인·발행 버전 |
| `recipient` | 대상자와 반입 근거, 마스킹 조회 |
| `request` | 대상자별 요청, 불변 스냅샷, 요청 상태와 멱등성 |
| `delivery` | HTML 이메일 렌더링, Outbox, SMTP 접수와 재시도 |
| `consent` | 보안 링크, 공개 세션, 항목별 결정과 최종 제출 |
| `audit` | 추가 기록 방식의 감사 이벤트와 조회 |
| `evidence` | PDF, JSON 스냅샷, SHA-256 매니페스트와 HMAC 검증 |
| `rights` | 열람·정정·삭제·처리정지·철회 요청과 처리 결과 |
| `retention` | 보유기간 산정, 보존 보류, 파기 승인·실행·확인 |

각 모듈은 `web`, `application`, `domain`, `persistence` 하위 패키지를 사용한다. 다른 모듈의 MyBatis Mapper를 직접 호출하지 않고 application 서비스의 공개 인터페이스를 사용한다.

## 7. 데이터 모델

### 7.1 계정과 권한

- `organization_unit`: 조직·부서 계층
- `admin_user`: 관리자 계정, 비밀번호 해시, 잠금·활성 상태
- `role`: 역할
- `permission`: 작업 권한
- `user_role`: 사용자와 역할 연결
- `role_permission`: 역할과 작업 권한 연결
- `user_scope`: 사용자에게 허용된 조직·처리업무 범위

### 7.2 정책과 템플릿

- `retention_policy`: 보유정책 논리 식별자와 현재 승인 버전
- `retention_policy_version`: 불변 승인 버전, 기산 이벤트, 기간, 유예기간, 파기 방식
- `processing_activity`: 처리업무 논리 식별자, 소유 부서, 상태와 현재 승인 버전
- `processing_activity_version`: 불변 승인 버전, 처리 목적, 근거 유형과 근거 상세
- `processing_data_item`: 처리업무 버전에 속한 일반 개인정보 항목과 필수 여부
- `consent_template`: 템플릿 논리 식별자
- `consent_template_version`: 불변 발행 버전, 제목, 안내 본문, 버전 해시
- `consent_item_definition`: 수집·이용, 제3자 제공, 선택 항목별 고지 데이터
- `template_review`: 검토·승인·반려 이벤트

### 7.3 대상자와 요청

- `recipient`: 대상자 식별자, 성명, 이메일, 반입 근거, 소유 부서
- `consent_request`: 대상자별 요청, 처리업무·보유정책·템플릿의 승인 버전, 만료시각, 요청 상태
- `consent_request_snapshot`: 발송 당시 표시 데이터와 정책을 고정한 JSONB, HTML 해시
- `consent_request_item`: 요청에 고정된 항목별 고지 데이터
- `mail_outbox`: 정확한 재시도를 위한 수신자, 제목, 암호화 또는 접근 통제된 HTML, 발송 상태
- `secure_link`: 토큰 HMAC, 만료·접속·완료·폐기 상태

### 7.4 응답과 증적

- `consent_response`: 요청별 하나의 최종 응답과 버전 번호
- `consent_response_item`: 항목별 `AGREE` 또는 `DISAGREE`
- `evidence_package`: PDF·JSON·매니페스트 경로, 해시, HMAC, 생성 상태
- `rights_request`: 권리요청 종류, 처리기한, 결정과 실행 결과
- `retention_job`: 파기 대상, 보존 보류, 승인·실행·확인 결과
- `audit_event`: 행위자, 대상, 작업, 결과, 이유, 추적 ID, 최소 메타데이터

모든 하위 데이터는 실제 상위 테이블을 참조하는 외래키를 가진다. 요청·응답·메일·증적을 고아 데이터로 만들 수 없다. 완료 증적을 보존해야 하는 경우에는 원 개인정보 삭제와 증적 최소 보존을 분리한다.

### 7.5 DB 역할

- `seal_owner`: 로그인할 수 없는 스키마 소유 역할
- `seal_app`: 애플리케이션 실행용 로그인 역할, 필요한 DML만 허용
- DB 변경 SQL은 PostgreSQL 관리자 또는 승인된 배포 절차가 `seal_owner` 권한으로 적용한다.
- 애플리케이션 계정에는 `SUPERUSER`, `CREATEDB`, `CREATEROLE`, 스키마 변경 권한을 부여하지 않는다.

DB가 아직 생성되지 않았으므로 기존 초기 SQL은 본 모델에 맞게 재작성한다. 최초 적용 이후에는 적용된 SQL을 수정하지 않고 순번 패치 파일을 추가한다.

## 8. 상태 모델

### 8.1 처리업무·보유정책

```text
논리 객체: ACTIVE ↔ INACTIVE

버전: DRAFT → REVIEW_REQUESTED → APPROVED → SUPERSEDED
                         └──────→ DRAFT (반려 의견 기록)
```

승인된 버전은 수정할 수 없다. 변경할 때는 같은 논리 식별자 아래 새 초안 버전을 만들고 다시 검토·승인한다. 새 버전이 승인되면 이전 승인 버전은 `SUPERSEDED`가 되지만 과거 요청은 자신이 참조한 버전을 계속 유지한다.

### 8.2 템플릿

```text
DRAFT → REVIEW_REQUESTED → APPROVED → PUBLISHED → RETIRED
```

`PUBLISHED` 버전은 수정할 수 없고 새 버전으로만 변경한다.

### 8.3 요청

```text
DRAFT → READY → ACTIVE → COMPLETED
                  ├────→ EXPIRED
                  └────→ CANCELLED
```

### 8.4 메일

```text
QUEUED → PROCESSING → SMTP_ACCEPTED
                    └→ RETRY_SCHEDULED → PROCESSING
                    └→ SEND_FAILED
```

`SMTP_ACCEPTED`는 릴레이 서버가 접수했다는 뜻이며 수신함 도착, 열람 또는 정보주체 확인을 뜻하지 않는다.

### 8.5 링크

```text
ISSUED → ACCESSED → COMPLETED
   ├────→ EXPIRED
   └────→ REVOKED
```

### 8.6 응답

```text
NOT_STARTED → IN_PROGRESS → SUBMITTED
                           └→ DECLINED_ALL
```

메일·링크·응답 상태는 서로를 대신하지 않는다. 예를 들어 메일이 `SMTP_ACCEPTED`여도 링크는 `ISSUED`, 응답은 `NOT_STARTED`일 수 있다.

## 9. 이메일과 단일 원본

1. 발행된 템플릿 버전과 대상자 변수로 `consent_request_snapshot`을 생성한다.
2. 스냅샷에는 제목, 기관, 목적, 구조화된 동의 항목, 보유정책, 거부권 안내와 철회 방법을 저장한다.
3. HTML 이메일과 웹 동의 화면은 같은 스냅샷을 입력으로 사용한다.
4. 이메일 본문에는 읽기 쉬운 고지 요약과 전체 고지, 기관 정보, 만료일과 기관 웹페이지 버튼을 표시한다.
5. 이메일 안에는 동의·미동의 입력 폼이나 최종 제출 기능을 넣지 않는다.
6. 이메일은 외부 JavaScript, 추적 픽셀과 제3자 리소스를 사용하지 않는다.
7. 재시도 시 내용이 바뀌지 않도록 최초 렌더링 HTML과 콘텐츠 해시를 Outbox에 고정한다.
8. SMTP 접수 결과만 기록하고 메일 열람 여부는 수집하지 않는다.

SMTP 실발송이 비활성화된 로컬 환경에서는 `mail_outbox`까지 생성하고 발송 작업은 실행하지 않는다. 관리자 화면에는 `발송 비활성화(로컬)` 상태를 명확히 표시한다.

## 10. 일회용 보안 링크

### 10.1 토큰

- Java `SecureRandom`으로 256비트 토큰을 생성한다.
- URL에는 Base64URL 인코딩한 원문 토큰만 사용한다.
- DB에는 서버 비밀키 기반 HMAC-SHA-256 결과만 저장한다.
- URL에 성명, 이메일, 요청번호와 같은 직접 식별자를 포함하지 않는다.
- 기본 만료기간은 7일이고 요청별로 1시간 이상 30일 이하에서 설정한다.
- 재발급하면 이전 링크를 `REVOKED`로 변경한다.

### 10.2 링크 스캐너 대응

1. 이메일 링크의 GET 요청은 토큰 유효성만 검사한다.
2. GET만으로 `ACCESSED`나 `COMPLETED` 상태로 변경하지 않는다.
3. 첫 화면은 개인정보 상세를 노출하지 않는 기관 확인 화면이다.
4. 사용자가 CSRF 보호된 `동의서 확인` POST를 실행하면 공개 동의 세션을 생성한다.
5. 서버는 토큰이 없는 깨끗한 URL로 리다이렉트하고 이때 `ACCESSED`를 기록한다.
6. 동의 화면은 자체 CSS만 사용하며 `Referrer-Policy: no-referrer`와 CSP를 적용한다.

### 10.3 제출

- 모든 표시 대상 항목에 `AGREE` 또는 `DISAGREE`가 선택되어야 한다.
- 기본 선택값과 전체 일괄동의는 제공하지 않는다.
- 최종 확인 화면에서 항목별 결정을 다시 표시한다.
- 제출은 서버 트랜잭션 하나에서 응답, 항목, 링크 완료와 감사 이벤트를 저장한다.
- 요청 행 잠금 또는 낙관적 버전으로 중복 제출을 차단한다.
- 같은 제출 멱등성 키의 재요청에는 기존 완료 결과를 반환한다.
- 완료 후 원응답을 수정하지 않는다.

## 11. 보안과 개인정보 보호

### 11.1 웹 보안

- Spring Security의 CSRF 보호를 관리자와 공개 제출 POST에 유지한다.
- 세션 쿠키는 `HttpOnly`, `SameSite=Strict`로 설정하고 운영에서는 `Secure`를 적용한다.
- 로그인 후 세션 고정 공격 방지를 위해 세션 식별자를 교체한다.
- JSP 출력은 기본적으로 이스케이프하고 허용된 템플릿 HTML만 화이트리스트 정제 후 사용한다.
- SQL은 MyBatis 바인딩 파라미터를 사용하고 문자열 조립 쿼리를 금지한다.
- Nginx와 애플리케이션에서 로그인, 링크 검증과 제출 요청 속도를 제한한다.
- 관리자·정보주체 화면에 CSP, `frame-ancestors 'none'`, `nosniff`, `no-referrer` 정책을 적용한다.

### 11.2 저장과 로그

- 비밀번호는 BCrypt로 단방향 해시한다.
- 보안 링크 원문과 HMAC 키를 DB에 함께 저장하지 않는다.
- HMAC 키는 저장소 밖의 권한 `0600` 파일 또는 운영 환경변수로 제공한다.
- 증적 디렉터리는 Tomcat 실행 계정만 읽고 쓸 수 있다.
- 목록·검색·오류 화면의 성명과 이메일은 마스킹한다.
- 애플리케이션 로그에는 토큰, 이메일 HTML, 응답 원문과 비밀번호를 기록하지 않는다.
- 접속 IP와 User-Agent는 기관 정책상 필요한 최소 형태로 축약해 감사 이벤트에 저장한다.

### 11.3 감사 이벤트

다음 작업은 성공·실패·거부 결과를 기록한다.

- 로그인·로그아웃·로그인 실패·계정 잠금
- 사용자·역할·범위 권한 변경
- 처리업무·근거·보유정책 변경
- 템플릿 검토·승인·발행·폐기
- 대상자 등록·조회·내보내기
- 요청 생성·활성화·재발급·취소
- SMTP 접수·실패·재시도
- 링크 확인·만료·폐기
- 동의 항목 선택과 최종 제출
- 증적 생성·다운로드·검증 실패
- 권리요청·보존 보류·파기

감사 테이블은 애플리케이션에서 UPDATE와 DELETE하지 않는다.

## 12. 증적과 파일

완료된 요청은 다음 산출물을 가진다.

- 사람이 읽을 수 있는 최종 PDF
- 요청 스냅샷 JSON
- 항목별 결정 JSON
- 주요 이벤트 목록 JSON
- 각 파일의 SHA-256과 식별자를 포함한 매니페스트 JSON
- 매니페스트의 HMAC-SHA-256

DB에는 파일 메타데이터, 상대 경로, 해시, HMAC, 생성 상태를 저장하고 파일 본문은 `/var/lib/seal/documents`에 저장한다. 파일명에는 개인정보를 사용하지 않고 UUID만 사용한다. 임시 파일에서 최종 파일로 원자적으로 이동한 후 `FINALIZED`로 변경한다.

PDF 생성은 OpenHTMLtoPDF와 PDFBox를 사용하고 기관이 승인한 재배포 가능한 한글 글꼴을 서버에 고정한다. 기준 HTML, CSS, 글꼴 버전을 증적 메타데이터에 기록한다.

## 13. 오류·재시도·동시성

- 모든 오류 응답은 사용자 메시지와 내부 오류코드를 분리한다.
- 화면에는 스택트레이스, SQL, SMTP 응답 전문과 개인정보를 표시하지 않는다.
- 요청마다 UUID 추적 ID를 발급해 로그와 감사 이벤트를 연결한다.
- SMTP 일시 오류는 최대 3회, 1분·5분·30분 간격으로 재시도한다.
- 영구 SMTP 오류 또는 최대 재시도 초과는 `SEND_FAILED`로 종료한다.
- Outbox 작업은 `FOR UPDATE SKIP LOCKED`로 중복 처리를 방지한다.
- 처리 중 프로세스가 종료되면 잠금 시각을 기준으로 10분 후 재처리할 수 있다.
- PDF 생성과 파기 작업도 작업 식별자와 멱등성 키를 사용한다.
- 최종 동의 제출과 철회는 각각 독립된 이력이며 서로 덮어쓰지 않는다.

## 14. 수명주기와 파기

- 처리업무를 활성화하려면 보유정책 연결이 필수다.
- 보유기간은 동의일, 프로그램 종료일, 목적 달성일 등 명시된 기산 이벤트에서 계산한다.
- 만료 대상은 일일 작업으로 `retention_job`에 생성한다.
- 법령·감사·분쟁 근거가 있을 때만 승인된 사용자가 보존 보류를 설정한다.
- 파기 작업은 실행자, 확인자, 대상 수, 성공·실패와 실패 이유를 기록한다.
- 원 개인정보와 최소 증적의 보유기간이 다르면 별도 정책으로 관리한다.
- 정책이 없는 운영 데이터는 생성하지 못하게 한다.

## 15. 수동 DB 변경 절차

Flyway와 Liquibase를 사용하지 않는다. 대신 다음 절차를 지킨다.

1. `database/NN_category/NNN_description.sql` 순번 파일을 작성한다.
2. 동일 변경의 검증 SQL을 함께 작성한다.
3. 데이터 손실 가능성이 있으면 역방향 SQL 대신 백업 복원 절차를 명시한다.
4. 전용 `seal_test` DB에서 적용·재적용 실패·검증을 확인한다.
5. 파일 SHA-256, 애플리케이션 버전, 적용자와 적용시각을 `db_change_history`에 기록한다.
6. 운영 반영 전 DB와 증적 파일의 일관된 백업을 생성한다.
7. 한 번 적용된 SQL 파일은 수정하지 않는다.

개발·시험·운영 DB와 계정은 분리한다. 테스트는 `seal_test`만 사용하며 `seal_dev`와 `seal_prod`를 초기화하거나 삭제하지 않는다.

## 16. 개발 프로세스

### 16.1 저장소와 변경 단위

- 기능 코드 작성 전에 로컬 Git 저장소를 초기화한다.
- `main`은 검증을 통과한 기준선으로 유지한다.
- 기능 단위로 작은 커밋을 만들고 SQL, 코드, 테스트와 문서를 함께 검토한다.
- 실제 비밀번호, HMAC 키, 개인정보 샘플과 운영 설정은 커밋하지 않는다.

### 16.2 TDD 순서

1. 도메인 규칙 또는 보안 요구사항을 표현하는 실패 테스트를 작성한다.
2. 테스트가 기능 부재 때문에 실패하는지 확인한다.
3. 테스트를 통과하는 최소 구현을 작성한다.
4. 관련 테스트와 전체 테스트를 실행한다.
5. 중복을 제거하고 이름과 모듈 경계를 정리한다.
6. 실제 JSP 화면과 대표 모바일 360px 화면을 확인한다.

PostgreSQL 동작이 필요한 Mapper 테스트는 H2로 대체하지 않는다. 별도 `seal_test` PostgreSQL에서 트랜잭션 롤백 방식으로 실행한다.

### 16.3 완료 기준

기능은 다음 조건을 모두 만족해야 완료다.

- 정상·실패·권한거부·중복요청 테스트가 통과한다.
- 서버 권한검사와 데이터 범위 검사가 있다.
- 개인정보 표시가 마스킹되고 로그에 원문이 남지 않는다.
- 상태 전이가 허용된 방향으로만 일어난다.
- 중요한 작업의 감사 이벤트가 생성된다.
- DB 변경 SQL과 검증 SQL이 함께 있다.
- JSP 키보드 조작, 레이블, 포커스와 오류 메시지를 확인한다.
- `mvnw test`와 WAR 패키징이 통과한다.
- 로컬 실행에서 홈, 로그인, 해당 기능과 오류 화면을 확인한다.

- HTTPS, 운영 도메인과 SMTP 실발송 활성화

## 18. 1단계 인수 기준

1. 부트스트랩 관리자 한 명을 DB에 안전하게 생성하고 다시 생성하지 않는다.
2. 올바른 비밀번호로 로그인하고 실패 누적 시 잠긴다.
3. 역할과 데이터 범위가 없는 사용자는 처리업무를 조회하거나 수정할 수 없다.
4. 처리업무에는 목적, 근거, 소유 부서, 일반 개인정보 항목과 보유정책이 필수다.
5. 승인되지 않은 처리업무는 템플릿이나 요청에서 사용할 수 없다.
6. 모든 등록·변경·승인·권한거부가 감사 이벤트로 남는다.
7. 목록의 성명·이메일 등 개인정보는 마스킹된다.
8. 적용 SQL의 순서와 SHA-256이 DB 변경 이력에 기록된다.
9. 전체 테스트와 실행형 WAR 패키징이 성공한다.
10. 로컬 환경은 SMTP와 HTTPS 없이 정상 개발할 수 있다.

## 20. 최종 결정 요약

- 이메일 본문은 안내와 고지용이며 동의 제출은 기관 웹페이지에서만 한다.
- 이메일과 웹은 하나의 불변 요청 스냅샷을 사용한다.
- 링크 보유 확인만 제공하며 실명 본인확인으로 표현하지 않는다.
- SMS, OTP와 전자서명은 전 범위에서 제외한다.
- 민감정보·고유식별정보·아동 업무는 처리하지 않는다.

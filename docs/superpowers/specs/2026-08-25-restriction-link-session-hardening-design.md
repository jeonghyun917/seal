# 처리제한·링크·공개 세션 보강 설계

## 1. 목적

이번 변경은 재검수에서 확인된 다음 네 가지 결함을 수정한다.

1. 직접 링크 발급 API가 처리제한 검사를 우회하는 문제
2. 기존 법적 보존이 있으면 처리제한 보류가 기록되지 않는 문제
3. 초안 수정·확정 과정에서 처리제한 대상자를 차단하지 않는 문제
4. 만료된 공개 동의 세션이 `ACTIVE` 상태와 `flow_hmac`을 유지하는 문제

전자서명, SMS, OTP, 본인확인, 이메일 열람 추적은 이번 변경 범위에 포함하지 않는다.

## 2. 설계 원칙

- 처리제한은 화면이나 메일 발송 서비스가 아니라 링크 발급의 핵심 서비스 경계에서도 강제한다.
- 법적 보존과 개인정보 처리제한은 동시에 존재할 수 있으며 서로의 사유를 덮어쓰지 않는다.
- 대상자 변경과 최종 확정은 신규 요청 생성과 동일한 처리제한 정책을 적용한다.
- 공개 동의 세션은 요청당 활성 세션을 하나만 유지하고 만료 시 식별용 HMAC을 지체 없이 파기한다.
- DB 변경은 Flyway 없이 수동 패치 SQL, 체크섬, 검증 SQL 절차를 따른다.

## 3. 링크 발급 경계

### 3.1 직접 API 제거

`ConsentRequestController`의 다음 관리자 API를 제거한다.

- `POST /admin/requests/{requestId}/activate`
- `POST /admin/requests/{requestId}/reissue`

화면에서 사용하는 발송 경로는 다음 두 개만 유지한다.

- `POST /admin/requests/{requestId}/deliver`
- `POST /admin/requests/{requestId}/redeliver`

발급된 원문 토큰은 기존과 같이 발급 직후 화면에서만 한 번 표시한다. URL 쿼리나 로그에는 토큰을 기록하지 않는다.

### 3.2 서비스 경계 방어

`SecureLinkManagementService.activate()`와 `reissue()`가 요청 대상자의 활성 처리제한을 직접 확인한다. 따라서 컨트롤러가 아닌 다른 내부 호출자가 추가되어도 제한을 우회할 수 없다.

메일 발송 서비스의 검사는 사용자에게 빠른 오류 응답을 주기 위한 선행 검사로 유지할 수 있지만, 최종 보안 경계는 링크 서비스다. 두 서비스는 동일한 `ConsentRestrictionQuery`와 서울 기준 업무일자를 사용한다.

처리제한이면 요청 상태, 기존 링크, 발송 대기 메일을 변경하지 않고 트랜잭션을 실패시킨다.

## 4. 법적 보존과 처리제한 공존

### 4.1 DB 제약 변경

기존 부분 유일 인덱스:

```sql
UNIQUE (consent_request_id) WHERE active
```

변경 부분 유일 인덱스:

```sql
UNIQUE (consent_request_id, hold_reason_code) WHERE active
```

이 변경으로 한 동의 요청에 `AUDIT`, `LITIGATION`, `RIGHTS_RESTRICTION` 등 서로 다른 활성 보류를 동시에 둘 수 있다. 같은 요청과 같은 사유의 활성 보류만 중복되지 않는다.

기존 인덱스를 삭제하기 전에 중복 데이터가 없는지 확인하고, 기존 `legal_hold` 행은 삭제하거나 변경하지 않는다.

### 4.2 처리제한 보류 등록

처리제한 보류 UPSERT의 충돌 대상도 `(consent_request_id, hold_reason_code) WHERE active`로 변경한다. 같은 처리제한 보류가 이미 있으면 기존 행을 유지하며 성공으로 처리한다. 다른 사유의 활성 보류는 변경하지 않는다.

처리제한 판정은 활성 상태이며 만료일이 없거나 현재 업무일 이후인 `RIGHTS_RESTRICTION` 행을 기준으로 한다.

## 5. 요청 생성·수정·확정 정책

다음 시점마다 대상자의 활성 처리제한을 확인한다.

1. 신규 초안 생성 직전
2. 초안 대상자 또는 참조 정보를 수정하기 직전
3. 초안을 `READY`로 확정하기 직전
4. 최초 링크 발급 및 재발급 직전

검사는 대상자의 조직 범위와 활성 상태를 먼저 검증한 다음 수행한다. 처리제한이면 `RequestBusinessConflictException`을 발생시키며 DB 변경이나 감사 성공 이벤트를 남기지 않는다.

확정 후 새롭게 설정된 처리제한은 링크 발급 경계에서 다시 차단한다. 이미 발급된 링크가 있는 대상자에게 처리제한이 승인되면 기존 링크의 즉시 폐기는 별도 정책 변경이므로 이번 범위에 포함하지 않는다.

## 6. 공개 동의 세션 수명주기

### 6.1 단일 활성 세션

유효한 보안 링크에서 새 공개 세션을 시작할 때 같은 동의 요청의 기존 `ACTIVE` 세션을 먼저 `EXPIRED`로 변경한다. 동시에 다음 값을 기록한다.

- `flow_hmac = NULL`
- `flow_destroyed_at = 현재시각`

보안 링크 행을 잠근 트랜잭션 안에서 기존 세션 만료와 새 세션 생성을 수행하여 같은 요청에서 활성 세션이 하나만 남도록 한다.

### 6.2 접근 시 만료 반영

조회 또는 제출 과정에서 세션 만료가 확인되면 해당 세션을 `EXPIRED`로 변경하고 HMAC을 파기한다. 만료된 흐름은 다시 사용할 수 없으며 사용자는 안내 메일의 원본 링크에서 새 세션을 시작해야 한다.

### 6.3 배치 정리

사용자가 다시 접근하지 않은 세션도 정리되도록 만료시각이 지난 `ACTIVE` 세션을 제한된 건수로 갱신하는 배치 작업을 추가한다. 단일 Rocky Linux 장비 운영을 고려해 별도 Redis나 Kafka 없이 PostgreSQL의 조건부 `UPDATE`를 사용한다.

배치 작업은 반복 실행에 안전해야 하며 이미 `COMPLETED` 또는 `EXPIRED`인 세션을 변경하지 않는다.

## 7. 트랜잭션과 동시성

- 링크 발급과 처리제한 확인은 하나의 서비스 트랜잭션에서 수행한다.
- 공개 세션 시작은 보안 링크 잠금, 기존 활성 세션 만료, 새 세션 삽입을 하나의 트랜잭션으로 처리한다.
- 세션 만료 SQL은 `session_status = 'ACTIVE'` 조건을 사용해 멱등성을 보장한다.
- 처리제한 보류 등록은 변경된 부분 유일 인덱스를 사용해 동시 중복 등록을 방지한다.
- DB 오류가 발생하면 권리요청 완료, 링크 발급, 메일 등록은 각각의 기존 트랜잭션 경계에서 함께 롤백되어야 한다.

## 8. 테스트와 검증

모든 수정은 실패하는 회귀 테스트를 먼저 작성한 뒤 최소 구현으로 통과시킨다.

### 8.1 단위·MVC 테스트

- 직접 `/activate`, `/reissue` API가 더 이상 매핑되지 않음
- 링크 서비스가 처리제한 대상자의 최초 발급과 재발급을 모두 거부함
- 초안 수정과 최종 확정이 처리제한 대상자를 거부함
- 새 공개 세션 시작 시 기존 활성 세션 만료가 호출됨
- 만료 세션 조회·제출 시 만료 처리와 HMAC 파기가 호출됨
- 세션 만료 배치가 비활성 설정일 때 실행되지 않고 활성 설정일 때 제한 건수만 처리함

### 8.2 PostgreSQL 16 이상 통합 테스트

- `AUDIT` 활성 보류가 있는 요청에 `RIGHTS_RESTRICTION`을 추가하면 두 행이 모두 활성으로 남음
- 같은 처리제한 보류를 반복 등록해도 활성 행은 하나임
- 처리제한이 있는 요청에서 직접 서비스 호출로 링크를 발급할 수 없음
- 반복 세션 시작 후 활성 세션은 하나이고 이전 세션의 HMAC은 `NULL`임
- 만료 배치 후 대상 세션이 `EXPIRED`이고 HMAC과 파기시각이 올바르게 갱신됨

### 8.3 최종 검증

- 신규 패치 SQL 체크섬과 DB 검증 SQL 실행
- 집중 테스트 실행
- 실제 로컬 PostgreSQL을 사용하는 통합 테스트 실행
- 전체 `mvnw verify` 실행
- `git diff --check` 실행

운영 Rocky Linux 설치, 백업, 인증서 및 운영 SMTP 검증은 사용자가 보류한 범위이므로 이번 검증에서 제외한다.

## 9. 완료 기준

- 처리제한 대상자의 요청 생성·수정·확정·링크 발급 경로가 모두 차단된다.
- 서로 다른 사유의 법적 보존과 처리제한 보류가 동시에 유지된다.
- 공개 동의 요청마다 활성 세션이 최대 하나이고 만료 세션의 HMAC이 정리된다.
- 기존 이메일 기반 동의, 증적, 권리요청, 파기 기능의 전체 테스트가 통과한다.
- 신규 DB 패치와 검증 SQL이 PostgreSQL에서 반복 가능한 절차로 문서화된다.
